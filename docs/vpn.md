# VPN identities and credentials — TTCP-012

VPN users are distinct from admin accounts. Admin bearer sessions may create,
update, disable and re-enable users; set `selected` server IDs or `all`; create
devices and revoke them; and request per-device, per-server credentials. Viewers
can read metadata but cannot mutate it or use the one-time secret handoff.

Routes are under `/api/vpn-users`. `POST` creates a user; `PATCH /{id}` updates
display name, expiration and quota; `PUT /{id}/enabled` changes availability;
`PUT /{id}/access` replaces the selected server set or chooses `all`. Device
routes are `GET/POST /{id}/devices` and `DELETE /{id}/devices/{device_id}`.
Credential routes are `GET /{id}/devices/{device_id}/credentials`, `POST` and
`DELETE /{id}/devices/{device_id}/credentials/{server_id}`. Create/revoke return
the durable job metadata (202). A repeated pending create or revocation returns
the existing job; after a failed job, the same request creates a retry job.

`all` evaluates against enabled servers at credential creation time, so future
eligible servers are included. Credential issuance for a new server is requested
per device. The quota counts enabled device rows, serializing additions through
the VPN user row lock. Per-server credentials never consume another device slot.
Device revocation, user disable, expiration and access removal mark affected
credentials `revoking` and insert revoke jobs in the same transaction. A disabled
user may be re-enabled, but previously revoked credentials require new issuance.
The worker scans for expired users and applies the same revoke path. Failed jobs
remain visible and retryable; a remote result is recorded only after the fixed
node helper reports success. Redis contains only job IDs.

The password is generated with the system CSPRNG and encrypted with the existing
`TTCP_AUTH_ENCRYPTION_KEY` before insertion. Jobs, audit details, logs and normal
API representations contain no password. After successful remote creation,
`POST .../credentials/{server_id}/download` returns username, password and
server address **once** to an admin. It sets `Cache-Control: no-store` and records
the handoff. Revocation immediately closes this handoff and erases ciphertext
after remote success. This handoff supplies credential material, not a rendered
TrustTunnel client configuration; configuration rendering/download remains a
separate integration step for the Client Portal.

Run migration `0006_vpn_lifecycle` before deploying the API or worker. The
managed node must first be re-bootstrapped with all three reviewed files in
`scripts/` so the fixed `/usr/local/sbin/ttcp-node-credential` helper and its
argument-free sudo rule are installed. The helper accepts only the two typed
operations, changes only `/opt/trusttunnel/credentials.toml`, and restarts the
existing service with rollback on failure. It accepts only the simple `[[client]]`
username/password format generated by the current Ansible template; other
credential-file formats require an explicit migration. Existing legacy CLI
credential files are not automatically imported into PostgreSQL.
