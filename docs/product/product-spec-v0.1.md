# TrustTunnel Control Plane — product baseline v0.1

Краткое описание целевого MVP. Источник требований — [Product & Architecture Specification v0.1](../architecture/product-architecture-spec-v0.1.md), прежде всего разделы 1, 9–16, 21, 25–26 и 31. Этот документ не заменяет спецификацию и не подтверждает наличие перечисленных функций в коде.

## Назначение и аудитория

Self-hosted система для управления небольшим парком TrustTunnel-серверов, VPN-пользователями и их устройствами. Начальный сценарий — один владелец и два Data Plane узла с возможностью постепенного расширения. Клиентский сценарий рассчитан в том числе на людей без технических знаний о VPN.

Control Plane управляет инфраструктурой, но не передаёт пользовательский VPN-трафик. Уже выданные действующие профили должны продолжать работать при недоступности Control Plane.

## Участники и права

| Участник | Назначение |
| --- | --- |
| Администратор (`admin`) | Управление серверами, конфигурацией, пользователями, устройствами и credentials; запуск административных операций. |
| Наблюдатель (`viewer`) | Просмотр состояния, мониторинга, журналов и аудита без привилегированных изменений. |
| VPN-пользователь | Самообслуживание собственных устройств и получение конфигураций для разрешённых серверов. Учётная запись VPN-пользователя отделена от административной. |

Авторизация выполняется на backend. Для административного входа MVP предусматривает пароль и TOTP; административные изменения должны быть аудируемыми.

## Самообслуживание и устройства

Администратор создаёт VPN-пользователя и выдаёт одноразовое приглашение. В Client Portal токен приглашения обменивается на сессию; в БД хранится только хеш токена. Пользователь выбирает разрешённый сервер, добавляет устройство и получает профиль через `tt://`. Дополнительные способы — скачивание TOML, QR и копирование конфигурации.

Квота задаётся параметром пользователя `device_limit`; по умолчанию это **3 устройства**. Проверки должны использовать значение параметра, сохраняя возможность его настройки в будущем. Это не лимит общего числа VPN-конфигураций.

Credentials принадлежат паре **Device × Server**. При доступе к N серверам у пользователя с тремя устройствами может быть до 3 × N таких связей. Отзыв одного устройства затрагивает только его credentials. Доступ пользователя может распространяться на выбранные серверы либо на все текущие и будущие серверы.

MVP предусматривает отключение пользователя и истечение срока доступа с отзывом соответствующих credentials. Полные правила жизненного цикла определены спецификацией.

## Границы MVP

- Управление вручную созданными VPS: подключение, предварительные проверки и операции жизненного цикла через Ansible.
- Admin Web и Client Portal; пользователи, устройства, серверные доступы и конфигурации.
- Долгие операции как jobs с отображением состояния и live logs; аудит и уведомления в Admin UI.
- Мониторинг узлов и сервисов, управление ревизиями конфигураций, удалённые зашифрованные резервные копии и восстановление через CLI/runbook.

## Вне MVP

- Коммерческий multi-tenant SaaS, billing, платежи и учёт трафика для billing.
- Создание VPS через API провайдеров и автоматическая географическая балансировка.
- Автоматический VPN subscription URL и multi-region HA Control Plane.
- Kafka, Kubernetes deployment и HashiCorp Vault.

Ansible Vault в существующем CLI остаётся отдельной технологией и не противоречит исключению HashiCorp Vault. Telegram-уведомления относятся к будущему развитию.
